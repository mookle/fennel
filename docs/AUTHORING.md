# Authoring style guide

Initially created for Claude, but relevant to all authors.

These rules apply to documentation, VCS text, error messages, release notes, and comments. They do not apply to code, identifiers, or command syntax.

## Terminology and semantics

- Use one name for one thing. Do not refer to the same item by two different names.
- Give each word one meaning. "Fall" means to move down, not to decrease.
- Don't use "mint" where "create" or "generate" has the same meaning.

## Language conventions

- Use British English spelling. "Colour", not "color"; "fulfilment", not "fulfillment".
- Use "an SKU", not "a SKU".

## Grammar and syntax

- Use a verb for an action. "Analyse the log", not "Perform an analysis of the log".
- No stacked auxiliaries. Write "This improves X", not "It is important to note that this may help to improve X".
- No "-ing" main verb where a simple tense works. Write "this release adds export to CSV", not "this release is adding export to CSV".
- Avoid run-on sentences where possible.

## Style and tone

- Use active voice. "The parser reads the file", not "The file is read by the parser".
- No marketing adjectives: seamless, robust, powerful, cutting-edge, effortless, world-class, next-generation, revolutionary.

## Document structure and organisation

- One topic per paragraph, maximum six sentences.
- For steps, use a numbered vertical list, one action per item, in the imperative form.
- Put a condition before its command.

## Typography and formatting

- No em dashes or en dashes. A spaced hyphen used as a dash is fine. This rule concerns the glyph, not the construct.
- Do not hard-wrap prose. This does not apply to code comments.
